让 AI 在聊天窗口里告诉你怎么改代码，和让它直接在你的电脑上改，是两回事。后者可以跑测试、读日志、改文件。那你交给它一个项目时，怎么保证它只在你划好的范围里干活？

最近 OpenAI 写了一篇文章，介绍 Codex 的沙箱是怎么设计的。我想用几个具体例子讲清楚：为什么光告诉模型「别动别的文件」不够，为什么 Codex 没把本地开发一律放进容器，以及「只允许写工作区」到底限制了什么。

## 为什么光在提示词里说「别动其他文件」不够？

比如，你让 Codex 修一个网站的测试，顺便告诉它：「只改这个项目，别动我的其他文件。」

Codex 改完以后，跑了一遍测试。这个项目的测试需要先编译代码，编译时会在项目外的一个目录里写缓存，省得下次从头编译。Codex 可能不知道还有这一步。只要那个目录不在允许写入的范围里，编译器就写不进去，测试也可能因此跑不完。

这个例子里，有三件事是分开做的：

1. **模型决定要跑测试。** 它根据你的任务，选了一条命令。
2. **Harness 负责启动命令。** 这是把模型和工具接起来的那层程序。它按当前的权限设置运行命令，如果需要更多权限，就走相应的审批规则。
3. **沙箱限制命令实际能做什么。** 编译器想写缓存时，系统会检查目标目录能不能写。就算这条命令又启动了别的程序，新程序也不会因此自动拿到更多权限。

所以，允许 Codex 跑测试，不等于允许测试程序往任何目录写文件。如果它确实需要用那个缓存目录，可以考虑只给这个目录开权限。让整条命令在沙箱外跑是另一回事：它会少一层限制，只剩下当前账号本来就有的系统权限。

## 为什么不直接用 Docker？

容器和虚拟机都能做隔离。问题是，本地开发往往要用到你电脑上已经装好的东西。

比如 iOS 项目要用 Mac 上的 Xcode 工具链和模拟器。把整个项目放进 Linux 容器，并不能把这些工具也搬进去。如果最后还是得把这一步交回 Mac，容器里的限制就管不到这一步，还得在 Mac 上另外设权限。

OpenAI 原文说，Codex 先定好权限，再用不同系统上的工具让规则生效。还是拿刚才写缓存的例子来说：

- **macOS 用 Seatbelt。** 这是 macOS 自带的沙箱。Codex 把「哪个目录不能写」告诉 macOS。编译器真去写时，macOS 会拒绝。
- **Linux 用 bubblewrap 和 seccomp。** bubblewrap 先给程序安排好能看到哪些目录、哪些能写、哪些只读。文件还在原地，不用另外复制一份。seccomp 管的是另一件事：程序做某些事要请系统帮忙，比如创建某类网络连接。这种底层请求叫「系统调用」，seccomp 可以拦下其中一部分。
- **Windows 用 MXC。** 这是微软提供的隔离工具。Codex 用它来启动程序，照样可以用你电脑上已经装好的开发工具，但能读写哪些文件、能不能联网，还是得按配置来。原文说 Codex 正在迁移到这套做法，目前只在兼容的设备上使用。

这样可以继续用现成的开发环境，不用为了跑测试重装一遍工具。但如果是涉及敏感资料的任务，我更愿意另开一个环境，只放这次要用的数据，而不是不断给日常电脑上的权限加例外。

## 能读文件、能改文件、能联网，是三件事

还是刚才那个项目。编译器可能需要读项目外已经装好的运行库，但没理由去改那些库。你可以允许它读运行库，只让它在项目目录里写文件。**「只能在项目里改文件」不等于「项目外的文件它一概看不到」。** 哪些地方能读，要看这次的权限配置。

网络也是单独管的。比如你关了终端的网络，终端里的程序就不能上网下载新依赖，但本机已经装好的库，只要原本有权读，还是能读。审查代码，我就只给读源码的权限；要改功能，再给项目目录的写权限。任务用不到的密钥和业务文件，我会放在它读不到的地方。

接进去的工具还要另外看。比如终端访问不了 GitHub，但你给 Codex 接了一个能读 GitHub Issue 的工具，它仍可能通过那个工具看到 Issue。原文讲的是本地 MCP 服务：Codex 默认不会用限制终端命令的同一个沙箱来启动它。所以接工具时，需要另外看它用哪个账号，能读什么、改什么，能不能替我发东西。

## 我什么时候需要亲自确认？

如果 Codex 只是在已经划好的范围里改代码、跑测试，那么就不需要每一步都点确认。如果它突然需要访问新目录、改外部系统，或者把内容发出去，才需要停下来问：为什么这一步非做不可？具体会碰到什么？能不能少给一点权限也做完？

这篇文章对设计 Agent 工作流很有帮助，所以在本地设计的时候也需要先想清楚三件事：这次要交付什么，正常做完最少要给哪些权限，哪一步必须让人重新判断。想清楚这些，再选模型、接工具。这样即使模型理解错了任务，它能动的东西也不会因此变多。
